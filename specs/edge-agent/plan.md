## Decisions
| ID | Chosen | Rejected | Why | Load-bearing assumption | Break signal → response |
|---|---|---|---|---|---|
| D-01 | MQTTnet 5.2.0.1603 (client; `MQTTnet.Server` same version in tests only) | Paho, HiveMQ client | MIT, .NET 10, in-process server for tests; APIs `WithCleanStart`, `WithSessionExpiryInterval`, `WithTlsOptions`, `AutoAcknowledge` confirmed in the 5.2.0.1603 DLL | v5 API stable | restore/API break → stop, re-pin, re-test |
| D-02 | SQLite via Microsoft.Data.Sqlite 10.0.13; one file; one shared connection factory (`EdgeDatabase`): WAL, `synchronous=FULL`, `busy_timeout=5000`; opened at host start | LiteDB, flat files | transactional append + sequence; durability needed by D-06 | local disk writable | corrupt/locked file at startup → host fails to start (no silent data loss); operator moves the file |
| D-03 | TLS mandatory (no plaintext option); username + password; password only from environment `Edge__Mqtt__Password`; with `CaCertificatePath` the chain must build to that CA only (`CustomRootTrust`) and the host name must match | optional TLS; mTLS | user decision; no credential or command exposure to a MITM | broker cert trusted by OS store or `CaCertificatePath` | TLS handshake fails → reconnect with backoff, never downgrade |
| D-04 | Topics `iiot/{edgeId}/telemetry`, `iiot/{edgeId}/commands`, `iiot/{edgeId}/command-results`; QoS 1; persistent session (`CleanStart=false`, expiry 24 h); client id = `edgeId`; retain false; subscribe with `RetainHandling=DoNotSendOnSubscribe`; `MaximumPacketSize` 16 KiB; exact topic match in handlers | QoS 2; per-tag topics | at-least-once with Cloud dedupe on (`edgeId`,`streamId`,`sequence`) / `commandId` | **broker ACL (wave 4): only the Cloud identity may publish `iiot/+/commands`; each Edge has its own credentials bound to its client id and may only publish/subscribe its own `iiot/{edgeId}/...` topics** | ACL missing → a leaked Edge password can command every Edge: block production rollout until wave 4 delivers ACLs |
| D-05 | Telemetry delivery at-least-once, strictly in `sequence` order; a row is deleted only after its PUBACK | delete on send | crash between PUBACK and delete re-sends a duplicate, never loses one | Cloud dedupes | — |
| D-06 | Commands serialized by the executor's own lock with an in-memory in-flight set; a `started` row is committed (synchronous=FULL) before the PLC write; a redelivered command with a stored or in-memory result gets that **same result re-published** (checked before the clock-rollback rejection); `started` without result after a restart → `unknown`/`write_outcome_unknown`, never re-executed; `completed` cannot be stored → result kept in memory, message not acknowledged until stored; `started` cannot be written or the log is full → no PLC write, `failed`/`edge_storage_error`; a log row is never deleted while its command could still be fresh | dedupe only after completion; new `duplicate` result | one command → one consistent outcome; a crash mid-write never causes a second actuation (wave-1 D-07) | SQLite commit durable before the write | — |
| D-06a | Deliberate exceptions to "one consistent outcome": results that are not stored (`edge_mismatch`, clock-rollback `clock_skew`, `edge_storage_error`) are not remembered — the Cloud must retry with a **new** `commandId` (wave-3 requirement); a process restart between a PLC write and storing `completed` turns the redelivery into `unknown`. A rejection (expired / clock_skew / catalog) that cannot be stored is **not published** and the message stays unacknowledged, so it is decided again later (user decision during task-05 review). Log rows live until the command's own expiry; `issuedAtUtc` is unbounded, so far-future commands can fill the 100,000-row capacity — accepted, relies on the wave-4 ACL | remembering everything; clamping expiry | storage is the failing component in those cases; clamping would let a forgotten id execute later | only the Cloud can publish commands | capacity rejections in the field → investigate the publisher, add a recovery design |
| D-07 | One shared MQTT connection (`MqttConnection`); it connects only after all subscriptions are registered; messages with no handler or a failing handler are **not** acknowledged | one client per service; auto-ack | no command is lost before the listener is ready | — | — |
| D-08 | Clock watermark: highest UTC time seen is persisted (`meta.last_seen_utc_ms`), always before any purge; while `now < watermark − 2 min` the Edge skips all purges and rejects every **new** command with `rejected`/`clock_skew` (known results are still re-published, D-06) | trusting the wall clock | a backward clock jump could make purged/old commands look fresh again | NTP eventually corrects the clock | frequent rollback warnings → fix NTP/RTC |

## Acceptance criteria
| ID | EARS criterion | Proof |
|---|---|---|
| AC-01 | If `Edge:EdgeId`, `Edge:Plc`, `Edge:Tags`, `Edge:Poll`, `Edge:Buffer` or `Edge:Mqtt` is invalid, or the buffer file cannot be opened, the host shall fail during start before any PLC or broker I/O; a valid catalog shall contain the configured tags. | task-01..04 |
| AC-02 | When samples are appended, the store shall assign consecutive `sequence` values of its `streamId` in the same transaction, survive a restart with the same `streamId`, and start a new `streamId` at 0 for a new database file. | task-02 |
| AC-03 | While rows are older than `MaxAgeHours` or exceed `MaxRows`, the store shall delete the oldest rows and log warnings whose dropped counts and sequence ranges sum to the rows removed; while the clock watermark shows a rollback, it shall not purge. | task-02 |
| AC-04 | When a poll cycle runs, the poller shall append one sample per catalog tag; if a read fails or yields a non-finite value it shall append `value=null`, `quality=bad`; after a `PlcUnavailableException` it shall mark the remaining tags `bad` without reading them and wait at least one interval before the next cycle. | task-03 |
| AC-05 | When the broker is reachable, the publisher shall publish queued samples in `sequence` order and delete each only after its PUBACK; while it is unreachable, samples shall stay queued and drain in order after reconnect. | task-04 |
| AC-06 | If the broker certificate does not chain to the configured CA or does not match the host name, the Edge shall not connect. | task-04 |
| AC-07 | When a command arrives, the executor shall check, in order, size/contract → `edgeId` → known result → clock rollback → freshness → catalog → log capacity, write to the PLC only if all pass and the `started` row is committed, and publish one `CommandResult` with the mapped outcome and reason. | task-05 |
| AC-08 | If a command id was already processed, the executor shall not write again: stored or in-memory result → that result re-published (also during a clock rollback); `started` without result after a restart → `unknown`/`write_outcome_unknown`; a row is never evicted while its command could still be fresh. | task-05 |
| AC-09 | If a command arrives before the listener is ready or its handling throws, the Edge shall not acknowledge it, so the broker redelivers it; a command queued while the Edge was offline shall be answered after start. | task-04, task-05 |
| AC-10 | If publishing a `CommandResult` fails, the executor shall keep it and re-publish the identical payload after reconnect (at-least-once). | task-05 |
